# 前端树状小说展示方案草案

## 目标

这个网站的核心不是“画一张复杂关系图”，而是让用户能够：

- 看懂一本树状小说目前有哪些世界线
- 顺着一条分支稳定阅读
- 在合适的位置继续续写或创建新分支
- 在节点很多时仍然不会迷路

因此，前端不应该把“全局树图”当成唯一主界面，而应该采用“阅读优先，图谱辅助”的双视图方案。

## 当前实现判断

基于当前代码，项目已经有了一个可继续演化的雏形：

- `frontend/src/pages/books/BookDetailPage.vue`
  - 作为书籍详情页，负责展示故事册入口和故事树
- `frontend/src/components/story/StoryTreeFlow.vue`
  - 作为图谱视图，当前使用 `vue-flow` 做节点连线展示
- `frontend/src/components/story/StoryTreePanel.vue`
  - 作为目录树视图，目前能力偏弱，尚未真正成为主交互面板
- `frontend/src/pages/story/StoryNodePage.vue`
  - 负责单节点详情、子分支列表、评论和互动
- `frontend/src/pages/story/StoryLineagePage.vue`
  - 负责一条完整分支的连续阅读体验
- `frontend/src/pages/story/StoryWritePage.vue`
  - 负责续写和分支创作

结论是：当前已经具备“阅读页 + 节点页 + 树图页”的基础结构，不需要推倒重来，但需要把树图从“技术演示”升级成“真正服务阅读和创作的导航界面”。

## 推荐产品方案

### 1. 视图分层

建议把书籍详情页重构为三个明确视图，而不是一个页面里只塞一张大图：

- 阅读视图
  - 面向第一次进入作品的用户
  - 重点展示作品简介、起始节点、推荐分支、最近活跃分支、入口按钮
- 树目录视图
  - 面向想快速理解结构的用户
  - 重点展示清晰的层级、分支标题、状态、作者、节点数
- 图谱视图
  - 面向想整体观察世界线走向的用户
  - 重点展示树结构、当前路径、高亮主分支、热门节点

默认打开“阅读视图”，而不是默认打开图谱。

### 2. 页面职责

建议页面职责收口为：

- `BookDetailPage`
  - 负责作品入口和三种视图切换
- `StoryNodePage`
  - 负责单节点详情、局部上下文、子分支选择、评论互动
- `StoryLineagePage`
  - 负责连续阅读，不承担全局结构探索
- `StoryWritePage`
  - 负责创作输入，不承担浏览树图职责

这样可以避免把所有任务都堆到一个页面里。

### 3. 核心用户路径

建议以这四条路径作为前端设计基准：

1. 新读者进入一本书
   - 先看简介和推荐入口
   - 再进入一条推荐分支开始阅读
2. 正在阅读的用户想切换世界线
   - 从 `StoryNodePage` 或 `StoryLineagePage` 进入树目录 / 图谱
   - 高亮当前所在路径
   - 快速跳到兄弟分支或祖先节点
3. 创作者想续写
   - 在节点详情页直接点击“沿此续写”或“创建分支”
4. 深度用户想研究结构
   - 打开图谱视图
   - 聚焦世界线密集区域、完结节点、热门节点

## 推荐交互结构

### A. 书籍详情页

建议把当前 `BookDetailPage` 拆成如下结构：

- 顶部 Hero 区
  - 标题、简介、阶段状态、总节点数、活跃作者数
  - `开始阅读`
  - `浏览结构`
  - `我要续写`
- 中部视图切换区
  - `阅读入口`
  - `树目录`
  - `全局图谱`
- 底部辅助信息区
  - 最近更新节点
  - 热门分支
  - 已完结分支

这里最重要的是，不让用户一进入页面就面对一张可能看不懂的大图。

### B. 树目录视图

`StoryTreePanel` 不应该只是一个普通树控件，而应该升级成“可导航的分支目录”：

- 每个节点显示：
  - 标题 / 分支名
  - 作者
  - 状态
  - 点赞数 / 子分支数
- 支持：
  - 展开 / 收起
  - 仅展开当前路径
  - 跳转到节点详情
  - 直接查看完整分支阅读

目录树的价值是“稳定”和“可扫描”，不是炫技。

### C. 图谱视图

图谱视图应该明确是“辅助理解结构”，而不是全文阅读界面。

建议保留这些能力：

- 缩放、拖拽、重置视图
- 点击节点跳转详情
- 高亮当前路径
- 区分节点状态和类型
- 只显示摘要，不显示长正文

建议避免这些事情：

- 不要在图节点里塞太多文本
- 不要让图谱承担评论、点赞、长文阅读
- 不要默认一次展开过多大树

### D. 连续阅读页

`StoryLineagePage` 的定位是对的，应该继续强化，而不是弱化。

建议增强：

- 当前分支面包屑
- 上一节点 / 下一节点快速跳转
- 当前分支终点的续写入口
- 跳转到兄弟分支的“分歧点切换器”

这页应当服务“沉浸式阅读”，视觉上比图谱更克制。

## 技术方案建议

### 1. 继续使用 Vue 体系

当前 `Vue 3 + TypeScript + Vue Query + Pinia + Naive UI` 的主框架不需要更换。问题不在框架，而在树图实现策略。

### 2. 升级图谱实现

当前 `StoryTreeFlow.vue` 使用的是旧 `vue-flow` 依赖，并且节点坐标由组件内手写递归生成。这条路不够稳。

建议改成：

- 图谱渲染层：`@vue-flow/core`
- 布局计算层：`d3-hierarchy/tree`

原因：

- 你的数据现在是标准树结构，天然适合 `d3-hierarchy/tree`
- `Vue Flow` 负责交互层会更轻松
- 布局和渲染分离后，后面更容易迭代节点样式和交互

只有当你以后出现“跨分支引用”“世界线合流”“非树边”时，再考虑引入 ELK 做复杂分层图。

### 3. 抽出图谱适配层

不要继续把“树数据转图数据”的逻辑写死在 `StoryTreeFlow.vue` 里。

建议新增一层前端适配：

- `frontend/src/features/story/tree-adapter.ts`
  - 输入：`StoryNodeTreeItem[]`
  - 输出：布局前树结构、布局后节点、边、高亮路径信息

这样做有三个好处：

- 组件变薄
- 类型边界清楚
- 以后切换布局算法不会污染页面组件

### 4. 统一故事树 UI 状态

建议新增一个轻量的故事树 UI store，例如：

- 当前选中节点 ID
- 当前高亮路径
- 当前展开节点列表
- 当前视图模式
- 当前图谱缩放状态

这样目录树、图谱、节点摘要卡才能联动，而不是各自独立。

## 建议组件拆分

建议把故事树相关组件整理成下面这组职责：

- `StoryTreeTabs`
  - 负责视图切换
- `StoryTreeSidebar`
  - 负责目录树、筛选、展开控制
- `StoryTreeGraph`
  - 负责全局图谱
- `StoryTreeNodeCard`
  - 负责图谱和目录中的统一节点摘要样式
- `StoryTreeInspector`
  - 负责显示当前选中节点的摘要、操作入口、跳转按钮

当前文件可以按这个方向逐步演化，而不需要一次性全部重命名。

## 实施顺序建议

建议按四期走，避免一次改太大。

### 第一期：界面收口

- 让 `BookDetailPage` 具备明确的三视图切换
- 把 `StoryTreePanel` 重新接回页面
- 给当前图谱加“点击节点 -> 打开详情”的稳定链路
- 给当前路径增加高亮逻辑

目标是先把信息结构做对。

### 第二期：图谱布局升级

- 引入 `@vue-flow/core`
- 引入 `d3-hierarchy`
- 把树布局逻辑从组件中抽到适配层
- 重写节点定位与边生成逻辑

目标是解决大树可读性和维护性问题。

### 第三期：阅读联动

- 从节点页进入图谱时自动聚焦当前位置
- 从连续阅读页跳转到对应分歧点
- 增加兄弟分支切换器
- 增加“仅看当前世界线 / 仅看主干 / 仅看未完结分支”筛选

目标是让图谱真正服务阅读。

### 第四期：性能和体验增强

- 大树默认折叠
- 分段加载或懒展开
- 图谱视窗内渲染优化
- 触屏拖拽与移动端适配

目标是为节点规模增长做准备。

## 设计方向建议

结合项目现有审美原则，建议保持：

- 黑白主色，局部冷色作为状态强调
- 图谱背景偏深，阅读页背景更克制
- 节点卡片用细线框和轻微辉光，不要过度发光
- 分支状态用颜色区分，但不要高饱和铺满全站

视觉上建议把：

- 阅读页做得安静
- 图谱页做得锐利
- 创作页做得专注

不要让三者长得完全一样。

## 需要避免的误区

- 不要把图谱页做成流程图编辑器风格
- 不要让节点卡片承担过多信息
- 不要把全文内容塞进图节点
- 不要默认把所有分支一次展开
- 不要为了图谱牺牲阅读体验

## 建议的近期任务清单

如果按当前项目节奏推进，最近一轮最值得做的是：

1. 重构 `BookDetailPage`，加入“阅读入口 / 树目录 / 全局图谱”切换
2. 让 `StoryTreePanel` 和 `StoryTreeFlow` 共享选中节点状态
3. 给图谱补当前路径高亮，而不是只画静态节点和边
4. 把 `StoryTreeFlow` 的数据转换逻辑抽离到独立模块
5. 后续再进入 `@vue-flow/core + d3-hierarchy` 的升级

## 结论

这个项目前端最合适的方向，不是变成一个“满屏关系图的网站”，而是做成一个：

- 默认适合阅读
- 同时可以探索分支结构
- 并且能自然进入创作动作

的树状叙事平台。

图谱是重要能力，但不应该压过阅读本身。对树状小说来说，最好的前端方案不是“图最多”，而是“读、找、写”三件事都顺畅。
